# Fresh CRC restore with Argo CD

Live test date: 2026-11-10. **Result: passed.** The source CRC instance was stopped and deleted, a fresh instance was started, Argo CD was provisioned independently, and four Applications were restored and synchronized automatically. All four OpenShift Routes returned the saved source content.

**No custom resource patches were needed.** Namespace names, Git references, destination names, project rules, and sync policies were already portable. See [RESULTS.md](RESULTS.md) for the recorded checks.

## Lifecycle

```text
Host Git server and artifact directory
                  |
crc start         |
install operator + Argo CD
configure namespaces and local cluster registration
create sample GitOps definitions
verify Applications, Pods, and Routes
crane export --include-gk ...
crane transform KubernetesPlugin
crane apply
save selected definitions and source evidence on the host
                  |
crc stop          |
crc delete        |  Git and export survive outside the VM
crc start         |
verify test namespaces are absent
install operator + Argo CD
recreate namespaces and target-issued local registration
apply exported definitions
verify automatic sync, new object UIDs, SCCs, and Routes
```

`crc stop` alone preserves the source cluster. The reset phase uses `crc delete --force`, which deletes **all data in the existing CRC instance**, including resources outside this example. The recorded run executed that reset with the user's explicit authorization. It preserved the bundle cache and host artifacts.

## Test setup

- CRC 2.63.0, OpenShift 4.22.7, Kubernetes v1.35.6.
- Six vCPUs, 14336 MiB RAM; the existing CRC disk configuration was 60 GiB.
- Community argocd-operator v0.18.0, installed through the pinned manual Kustomize configuration in [operator/](operator/kustomization.yaml), before migration on both clusters.
- Argo CD v3.3.10, instance `crane` in `crane-gitops-crc`.
- Official Crane v0.11.0 and embedded Kustomize v5.8.1.

The operator is installed manually, independently of Crane. This run does not validate OLM installation or the Red Hat OpenShift GitOps distribution.

### Host-retained Git and evidence

The Git repository must remain available after the source VM is deleted. [git-server/Containerfile](git-server/Containerfile) builds a public, read-only Git daemon that runs in a host Podman container named `crane-crc-git`. Its repository and all evidence live under `/tmp/opencode/argocd-crc/`, outside the CRC VM.

The recorded repository URL was `git://192.168.8.125:9418/apps.git`. Use a stable host address reachable from CRC when repeating the test. The runner records the URL during `host-git`; later phases reuse it. It rejects changing that URL after source validation.

CRC's documented `host.crc.testing` alias resolved but timed out on this host. Publishing the server and using the host's reachable LAN address worked from the Argo CD repo server. No firewall changes were needed in this run. The container publishes port 9418 and serves only the disposable sample repository; it contains no credentials.

## Run the flow

Requirements are CRC, a valid CRC pull-secret configuration, `oc`, Git, Podman, curl, Python 3 with PyYAML, and Crane v0.11.0. Cluster setup and image pulls need network access. The Git server image is built once on the host and survives CRC deletion.

Run from the planning repository root. Use a new artifact directory for a new replay. The recorded container name and directory are already in use; inspecting the current run does not require running the lifecycle again.

### Prepare the host Git service

```bash
python3 playground/argocd-migration/live/crc/run_crc.py host-git \
  --repo-url git://192.168.8.125:9418/apps.git \
  --work-dir /tmp/opencode/argocd-crc \
  --crane /tmp/opencode/argocd-crane-v0.11.0/crane_linux_amd64
```

The host server is separate from CRC. For an intentional new replay, stop/remove the previous `crane-crc-git` container before creating another server with that name, and choose a new work directory.

### Execute the phases in order

Every phase uses the same arguments. For example:

```bash
python3 playground/argocd-migration/live/crc/run_crc.py start-source \
  --work-dir /tmp/opencode/argocd-crc \
  --crane /tmp/opencode/argocd-crane-v0.11.0/crane_linux_amd64
```

Replace `start-source` with each subsequent phase in this order:

| Phase | Action |
| --- | --- |
| `start-source` | Enable CRC host-network access, start CRC, save a flattened source kubeconfig, wait for the Node, record identity. |
| `bootstrap-source` | Install the pinned operator, provision Argo CD, create workload namespaces and local registration, verify Git access. |
| `source` | Create the project, two standalone Applications, and ApplicationSet; verify all four workloads through Routes. |
| `export` | Run filtered Crane export and default cleanup; retain four desired-state resources and source evidence on the host. |
| `reset` | Check required artifacts and source identity, run `crc stop`, then `crc delete --force`. |
| `start-target` | Start CRC from its cached bundle, save a new kubeconfig, and assert all test namespaces are absent. |
| `bootstrap-target` | Install the operator and Argo CD before import; create namespaces and target-issued registration; verify unchanged Git access. |
| `import` | Run target server-side validation and apply the four exported definitions to the existing target instance. |
| `verify` | Check automatic sync, exact Application specs/revisions, new UIDs, SCC-assigned users, and HTTP through all Routes. |

The runner uses explicit source and target kubeconfig files rather than relying on the default current context. CRC lifecycle output is captured in private logs because CRC startup can print credentials. The artifact directory has mode 0700 and kubeconfig/private log files have mode 0600. Keep these artifacts outside version control.

### Export scope

The export phase effectively runs:

```bash
crane export --kubeconfig /tmp/opencode/argocd-crc/source.kubeconfig \
  --context admin -n crane-gitops-crc \
  --include-gk argoproj.io/Application \
  --include-gk argoproj.io/ApplicationSet \
  --include-gk argoproj.io/AppProject \
  --crd-skip-group argoproj.io \
  --export-dir /tmp/opencode/argocd-crc/export
```

The runner reads the actual context name from the flattened kubeconfig. It does not export the instance CR, credentials, generated infrastructure, workload Pods, or Namespace objects.

The seven exported CRs become five after generic Kubernetes cleanup. A selection-only stage excludes the source `default` project, leaving four definitions. Its Kustomization lists only resources; it has no patches or namespace override. The runner verifies that selection did not change the materialized resources.
